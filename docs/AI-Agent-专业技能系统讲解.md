# AI Agent 工程专业技能系统讲解

## 导读

这份手册面向已经零散接触过 AI Agent、后端工程和检索技术，但还没有形成系统知识结构的求职者。它不把简历中的关键词继续堆叠，而是回答四个更实际的问题：每项技术是什么，它解决什么问题，它在真实系统中如何与其他技术配合，以及掌握到什么程度才适合在简历和面试中使用“熟练”“掌握”或“了解”。

全文按五类能力展开。每一类先逐项解释，再用一条完整工程链路把知识串联起来。最后通过一个企业知识助手案例，把五类能力连接成从请求进入、Agent 决策、知识检索、工具执行、状态持久化到评测与安全的完整系统。

建议阅读时把“能复述”与“能实现”分开。理解概念是第一层，能够写出最小示例是第二层，能够处理失败、性能、安全和可观测性问题才是工程能力。简历措辞应以可以展示的代码、测试、指标或复盘记录为依据。

## 1 全局学习地图

### 1.1 五类能力分别负责什么

| 能力类别 | 核心问题 | 典型产物 |
|---|---|---|
| 编程与工程 | 怎样把系统稳定地开发、部署和维护 | API、数据库模型、异步任务、容器、测试 |
| Agent 开发 | 怎样让模型围绕目标进行规划、调用工具并保持状态 | Agent 图、工具协议、状态机、检查点 |
| RAG 与知识检索 | 怎样从外部知识中找到可用证据并交给模型 | 文档索引、混合检索、重排、检索评测 |
| Agent 评测与稳定性 | 怎样证明系统有效，并在失败时安全恢复 | Trace、评测集、指标、重试和安全策略 |
| LLM 基础与优化 | 模型为何能生成、何时用提示词、检索或微调 | Prompt、Function Calling、SFT 或 LoRA 方案 |

这五类能力不是五套独立知识。后端工程提供运行环境和数据边界；Agent 决定下一步动作；RAG 提供证据；评测与稳定性约束系统质量；LLM 基础帮助开发者理解模型的能力边界并选择合适的优化方式。

### 1.2 学习深度的四个层级

| 层级 | 判断标准 | 简历建议 |
|---|---|---|
| 了解 | 能解释概念、适用条件和主要限制 | 使用“了解”“理解” |
| 会用 | 能按文档完成最小实现并调试常见问题 | 使用“熟悉”“具备使用经验” |
| 掌握 | 能独立设计、实现、测试，并解释关键取舍 | 使用“掌握”“具备开发经验” |
| 熟练 | 在多个场景中处理过性能、故障、安全和维护问题 | 谨慎使用“熟练” |

当前最合适的目标不是一次记住所有术语，而是为每项技术形成“定义、机制、场景、取舍、实践证据”五格笔记。面试官通常会沿着这五个方向连续追问。

## 2 编程与工程

### 2.1 Python

Python 是 AI 应用和后端服务中常用的通用编程语言。对 Agent 工程而言，重要的不只是语法，还包括类型、数据模型、异常、并发、包管理和测试。类型注解能让工具参数、状态对象和 API 输入更清晰；数据类或 Pydantic 模型能把松散字典变成可验证的结构；异常体系决定失败能否被识别和恢复。

需要重点理解 Python 的对象模型、可变与不可变对象、迭代器和生成器、装饰器、上下文管理器、类型注解以及异步语法。生成器适合流式处理大文件或模型输出；上下文管理器适合管理数据库会话和文件；装饰器常用于鉴权、重试和埋点；类型注解则是 FastAPI 自动生成接口契约的基础。

常见误区是把“能写脚本”当作“熟练 Python”。工程代码还需要明确模块边界、避免共享可变状态、正确处理资源释放，并能通过日志和测试定位问题。可验证的练习是实现一个带类型注解、异常分类、异步调用和单元测试的小型服务。

### 2.2 FastAPI

FastAPI 是基于 ASGI 的 Python Web 框架，适合构建类型明确、支持异步 I/O 的 API 服务。它会读取函数签名和 Pydantic 模型，完成请求解析、数据校验和 OpenAPI 文档生成。依赖注入机制可以统一提供数据库会话、当前用户和权限检查。

一个请求通常经过路由匹配、依赖解析、输入校验、业务服务、持久化和响应序列化。开发时应把路由层保持得较薄：路由负责 HTTP 语义，服务层负责业务规则，仓储层负责数据访问。这样测试时可以绕开网络层验证核心逻辑。

需要掌握同步与异步路由的边界。只有当下游库也支持异步并且任务主要等待网络或磁盘时，`async def` 才能提高并发能力。CPU 密集计算直接放进事件循环会阻塞其他请求，应转移到进程池或任务队列。

### 2.3 异步任务

异步包含两类常被混淆的机制。第一类是单进程事件循环中的异步 I/O，适合同时等待数据库、HTTP 和模型响应；第二类是脱离请求生命周期的后台任务，适合耗时较长、需要重试或需要持久化状态的工作。

轻量任务可以使用框架自带后台任务，但重要任务通常需要 Celery、Dramatiq、RQ、Temporal 或云队列。请求处理器先写入任务记录并返回任务标识，Worker 再消费任务。可靠系统还要考虑消息确认、可见性超时、失败队列、幂等键、重试退避和任务状态查询。

异步不等于自动变快。它提高的是等待型任务的并发利用率。若任务需要严格的流程恢复和长时间等待，持久工作流通常比普通消息队列更合适。

### 2.4 RESTful API

REST 是一种围绕资源设计网络接口的风格。资源用 URI 表示，HTTP 方法表达操作，状态码表达结果。`GET` 应读取资源，`POST` 常用于创建或触发非幂等动作，`PUT` 表示整体替换且应具有幂等性，`PATCH` 表示部分更新，`DELETE` 表示删除。

好的 API 不只需要路径规范，还需要稳定的请求和响应模型、分页、过滤、错误码、鉴权、限流、版本管理和幂等设计。对 Agent 系统尤其要区分“创建一个执行任务”与“真正执行外部副作用”。高风险操作宜先生成计划或审批请求，再通过单独接口确认执行。

常见错误包括把所有操作都设计成 `POST /doSomething`、用 200 状态码包住全部错误、返回不稳定的自由文本，以及没有为重复请求设置幂等键。

### 2.5 SQLAlchemy 与 Alembic

原简历中的 SQLAIchemy 和 AIembic 应分别写为 SQLAlchemy 和 Alembic。SQLAlchemy 提供数据库连接、SQL 表达式和对象关系映射。ORM 模型把表映射为 Python 类，但开发者仍需理解 SQL、索引、事务和查询计划，否则容易产生 N 加一查询、全表扫描或过长事务。

SQLAlchemy 的关键概念包括 Engine、连接池、Session、事务和模型关系。Session 代表一个工作单元，负责跟踪对象变化并在提交时生成 SQL。它不应作为跨请求的全局对象使用。异步版本需要异步驱动和 `AsyncSession`，但异步接口不会消除数据库锁和慢查询。

Alembic 管理数据库结构版本。开发者通过迁移脚本描述升级和回滚步骤，并在不同环境中按顺序应用。自动生成迁移只能作为草稿，重命名字段、数据回填、大表加索引等操作需要人工审查。生产迁移还要考虑向前兼容，例如先添加可空字段并双写，再回填，最后收紧约束。

### 2.6 MySQL 与 PostgreSQL

MySQL 和 PostgreSQL 都是关系型数据库，支持事务、索引、约束和复杂查询。关系型数据库适合保存用户、任务、权限、执行记录和业务对象，因为这些数据需要一致性和可查询性。

必须理解 ACID、隔离级别、主键、唯一约束、外键、B 树索引和事务边界。索引能加速读取，但会占用空间并增加写入成本；联合索引是否生效与列顺序和查询条件有关。事务过大会增加锁竞争，事务过小又可能破坏业务原子性。

PostgreSQL 在 JSONB、全文检索、扩展生态和复杂 SQL 方面较强，也常通过 pgvector 保存向量。MySQL 在大量传统 Web 场景中成熟稳定。选型应基于已有基础设施、团队经验、数据类型和查询需求，而不是简单判断谁更先进。

### 2.7 Redis

Redis 是内存数据结构服务器，常用于缓存、会话、限流、分布式锁、短期状态和消息流。常用结构包括字符串、哈希、集合、有序集合和 Stream。因为主要数据位于内存中，Redis 读写延迟通常较低，但容量和持久性策略需要单独设计。

缓存的核心难点是失效策略，而不是读写命令。需要处理缓存穿透、击穿、雪崩、热点键和数据一致性。常见方案包括合理 TTL、空值缓存、请求合并、随机过期时间以及写数据库后删除缓存。

分布式锁不能只使用“存在即成功”的简单逻辑。至少要使用唯一持有者标识、原子加锁和带条件释放，并理解锁过期与业务尚未完成之间的风险。对严格一致的业务，数据库约束或持久工作流往往比 Redis 锁更可靠。

### 2.8 Linux

Linux 是大多数后端服务和容器的运行环境。应掌握文件与目录、权限、进程、信号、端口、环境变量、日志和资源观察。常用排查路径是先确认进程是否存在，再检查端口监听、日志错误、CPU 和内存、磁盘空间、网络连通以及依赖服务。

关键命令本身不是重点，重点是形成诊断顺序。例如服务超时时，应区分应用处理慢、数据库慢、DNS 或网络失败、连接池耗尽和下游限流。权限方面需要理解用户、用户组、读写执行位和最小权限原则。

### 2.9 Git

Git 是分布式版本控制系统。Commit 是一组可追踪的变更，Branch 是指向提交的可移动引用，Merge 和 Rebase 用不同方式整合历史。工程中应做到小步提交、提交信息明确、改动范围单一，并在合并前通过测试。

需要掌握工作区、暂存区和提交历史的区别，以及冲突产生的原因。`rebase` 可以整理本地历史，但不应随意重写多人共享分支。安全习惯包括提交前查看 diff、不提交密钥、使用 `.gitignore`、通过代码评审保护主分支。

### 2.10 Docker

Docker 使用镜像描述应用及其依赖，再通过容器提供隔离的运行环境。Dockerfile 中每条指令形成镜像层；合理排序可以提高缓存命中率。多阶段构建能把编译环境与运行环境分开，减少最终镜像体积和攻击面。

容器不是完整虚拟机，也不是安全边界的全部。生产环境应使用非 root 用户、固定基础镜像版本、最少依赖、健康检查和资源限制。数据不应依赖容器可写层，数据库和持久文件需要使用外部存储。

### 2.11 Pytest

Pytest 是 Python 测试框架。测试通常分为单元测试、集成测试、契约测试和端到端测试。Fixture 用于准备和清理依赖，参数化测试可以覆盖多组输入，Monkeypatch 或 Mock 可以隔离外部系统。

有效测试关注可观察行为，不依赖实现细节。异步代码需要异步测试支持；数据库测试需要隔离事务或独立测试库；外部模型和工具应使用可重复的 Fake 或录制响应。覆盖率只说明代码是否被执行，不能证明断言质量。

### 2.12 编程与工程如何串联

以“提交一项 Agent 任务”为例：FastAPI 接收 REST 请求，Pydantic 校验输入，服务层使用 SQLAlchemy 在 PostgreSQL 中创建任务记录，并把耗时执行交给异步 Worker。Redis 可以保存短期进度或提供限流。应用被构建为 Docker 镜像，在 Linux 环境中运行。Git 保存每次改动，Pytest 验证路由、业务规则、数据持久化和失败行为，Alembic 保证数据库结构能够随版本演进。

这条链路的关键是边界清晰。HTTP 请求不承担长任务，数据库事务不跨越模型调用，缓存不作为唯一事实来源，后台任务拥有幂等键，每次改动都有测试和提交记录。

## 3 Agent 开发

### 3.1 Agent 的基本结构

Agent 是一个围绕目标反复执行“观察、决策、行动、更新状态”的系统。语言模型通常负责理解目标和提出下一步，工具负责访问外部世界，状态层记录上下文，控制层约束循环何时继续、暂停或结束。

普通聊天模型一次生成答案，Agent 则可能多轮调用搜索、数据库或业务 API。模型输出具有不确定性，因此权限、预算、超时和终止条件不能完全交给模型自由决定。

### 3.2 ReAct

ReAct 把推理与行动交替组织。模型根据当前观察选择工具，工具返回结果，模型再决定下一步。它适合路径无法预先确定、需要逐步探索的任务，例如排查问题或跨多个数据源搜集信息。

优点是灵活、容易接入新工具。缺点是调用次数可能较多，容易循环或偏离目标。工程实现需要限制最大步数、校验工具参数、记录轨迹，并把敏感决策放在确定性策略层。

一个简化循环是：接收问题，选择检索工具，读取结果，判断证据是否足够，不足时改写查询，再生成带证据的答案。若达到步数或时间预算仍无可靠证据，应明确失败或请求澄清。

### 3.3 Plan and Execute

Plan and Execute 先把复杂目标拆成步骤，再由执行器逐项完成。它适合依赖关系清晰、步骤较多、需要进度展示或中途审批的任务。计划应包含步骤目标、依赖、输入、预期输出和风险级别。

计划不是不可修改的静态清单。执行结果可能使后续步骤失效，因此系统需要重规划能力。规划器也不应直接拥有高风险工具权限，执行器在每一步仍需经过参数校验和策略检查。

与 ReAct 相比，Plan and Execute 更便于审计和恢复，但前期计划可能不准确，控制逻辑也更复杂。实践中常把两者结合：外层用计划管理阶段，单个阶段内部使用有限步数的 ReAct。

### 3.4 LangChain 与 LangGraph

LangChain 提供模型、Prompt、工具、检索器和链式调用的抽象，适合快速组合 LLM 应用。LangGraph 用图来描述有状态流程，节点执行逻辑，边决定流转，状态在节点之间传递。它更适合存在循环、分支、人工审批和检查点的 Agent。

使用框架前应先画清状态和边界，否则容易把业务规则隐藏在大量框架对象中。需要重点掌握状态 Schema、节点输入输出、条件边、检查点、错误处理和可观测性。框架能减少样板代码，但不会替你定义安全策略或业务一致性。

### 3.5 任务编排

任务编排把目标拆为可执行节点，并管理依赖、并发、重试、暂停和取消。简单顺序任务可以用函数链，复杂任务常表示为有向无环图或状态机。若流程包含等待审批或长时间运行，则需要持久化编排。

设计任务节点时，应明确输入、输出、副作用、重试策略和幂等键。只读节点通常可以安全重试；发送邮件、创建工单或扣款等副作用节点必须先检查是否已经成功。编排层还应保存每个节点的状态，避免进程重启后从头重复执行。

### 3.6 Tool Calling

Tool Calling 让模型按照预先定义的名称和参数结构请求工具。模型负责提出调用意图，应用负责校验参数、检查权限、真正执行并返回结果。工具 Schema 应窄而清晰，枚举和必填字段应尽量明确。

工具执行链至少包含参数验证、身份和权限检查、风险策略、超时、调用、结果清洗和审计记录。不要把模型生成的参数直接拼接到 SQL、Shell 或 URL 中。对于删除、付款、发布等高风险操作，应增加人工确认或双阶段提交。

### 3.7 结构化输出

结构化输出要求模型返回符合 JSON Schema 或数据模型的结果。它适合计划、分类、评分和工具参数，因为程序可以确定性解析。Pydantic 等工具能够校验字段类型、范围和枚举。

结构正确不代表语义正确。模型可能生成合法但不存在的 ID，或给出格式正确但风险错误的计划。因此结构校验之后仍需要业务校验。失败时可尝试有限次数的修复，但不能无限重试。

### 3.8 上下文管理

上下文包括系统指令、用户消息、工具结果、检索证据、长期记忆和当前状态。模型上下文窗口有限，信息越多也不一定越好。无关内容会增加成本，甚至降低模型对关键约束的注意力。

常见策略包括保留最近对话、压缩早期历史、按需检索长期记忆、为工具结果设置大小限制，以及把确定性状态放在数据库而不是聊天文本中。摘要需要保留未完成任务、已做决策、约束和证据来源，不能只保留泛泛主题。

### 3.9 状态持久化

状态持久化使 Agent 在进程重启、网络失败或人工等待后继续执行。通常需要保存任务状态、当前节点、步骤输出、外部副作用记录、审批状态和版本信息。检查点应在关键节点之后原子写入。

恢复时不能只读取“执行到第几步”。系统还需判断上一次工具调用是否已经在外部成功。可靠做法是为副作用生成稳定幂等键，重试前先查询执行记录或外部系统，再决定继续、补偿还是等待人工处理。

### 3.10 MCP 协议

Model Context Protocol 是连接 AI 应用与工具、资源和提示模板的开放协议。它通过统一的能力发现和调用方式，降低每个客户端为每个数据源编写专用集成的成本。MCP Server 暴露工具或资源，MCP Client 建立连接并发起调用。

理解 MCP 时要区分协议互操作性与业务安全。协议能统一描述工具，但身份、授权、租户隔离、审计和数据脱敏仍需要系统实现。客户端也不能因为某个 Server 声称提供工具就自动信任它。

### 3.11 Multi Agent 路由与 Handoff

多 Agent 系统把不同任务分配给具有不同指令、工具或知识的 Agent。路由可以基于规则、分类模型或 LLM。Handoff 表示当前 Agent 把控制权和必要上下文移交给另一个 Agent。

多 Agent 的价值在于隔离职责和上下文，不在于 Agent 数量。若一个流程用单 Agent 和几个工具就能清晰实现，引入多个 Agent 只会增加延迟和调试难度。Handoff 时应传递目标、已完成工作、证据、约束和待办，避免复制全部聊天历史。

评估多 Agent 还要关注路由准确率、交接后的信息损失、重复工作、循环交接和总成本。权限应按 Agent 职责分配，不能让所有 Agent 共用最高权限。

### 3.12 Agent 开发如何串联

用户提出复杂任务后，路由器判断由哪个 Agent 负责。外层 Plan and Execute 生成阶段计划，LangGraph 保存状态并控制分支。执行节点可以使用 ReAct 选择检索或业务工具，所有 Tool Calling 都经过结构校验、权限策略和超时控制。长任务在节点完成后写检查点；需要专家能力时执行 Handoff，只传递必要状态。MCP 为不同工具提供统一接入方式，但实际授权仍由应用控制。

## 4 RAG 与知识检索

### 4.1 RAG 的目标

检索增强生成先从外部知识库找到相关证据，再让模型基于证据回答。它适合知识经常变化、需要来源或包含私有数据的场景。RAG 的核心不是向量数据库，而是从原始文档到可靠答案的整条数据链路。

典型流程包括采集、解析、清洗、分块、建立稀疏和稠密索引、召回、重排、上下文组装、生成和引用。任何一环出错都会影响最终答案。

### 4.2 文档解析

文档解析把 PDF、Word、网页、表格或图片转换成带结构的文本。高质量解析应保留标题层级、段落、列表、表格、页码和来源元数据。扫描件需要 OCR，复杂 PDF 还要处理多栏、页眉页脚和阅读顺序。

只提取纯文本会丢失结构。例如表格中的数字如果脱离行列标题，检索到后也无法解释。工程上需要为解析结果设计统一 Schema，并记录文档 ID、版本、权限和原始位置，便于引用和删除更新。

### 4.3 分块

分块把长文档拆成可检索单元。块太小会丢失上下文，块太大则引入噪声并占用模型窗口。常见策略包括固定长度、按标题和段落切分、滑动重叠以及针对代码或表格的专用切分。

分块应与问题粒度匹配。制度问答可能适合按条款切分，技术文档适合保留标题路径，表格需要将表头与行内容组合。评估分块不能只看字符数，应检查答案证据是否能在一个或少量块中完整出现。

### 4.4 Embedding 选型

Embedding 模型把文本映射为向量，使语义相近的文本在向量空间中更接近。选型应考虑语言、领域、最大输入长度、向量维度、延迟、成本、部署方式和基准效果。

更大模型不一定适合所有系统。中文或多语言场景要使用相应数据训练的模型；代码检索需要代码能力；私有部署还要考虑显存和吞吐。更换 Embedding 模型通常需要重建全部向量索引，因此模型版本必须写入索引元数据。

### 4.5 BM25

BM25 是经典稀疏检索算法，根据词在当前文档中的频率、在全部文档中的稀有程度和文档长度计算相关性。它擅长精确关键词、产品编号、人名和错误码，对没有语义相似词的专有名词尤其有效。

它的限制是难以理解同义表达和语义关系。中文场景还依赖分词质量。BM25 通常作为强基线，并与向量检索组合使用。

### 4.6 向量检索与混合召回

向量检索按照 Embedding 相似度召回语义相关块，能够匹配不同措辞表达的相同意图。近似最近邻索引通过牺牲少量精确度换取检索速度，常见索引方法包括 HNSW 和 IVF。

混合召回同时使用 BM25 与向量检索，再合并两组结果。常用合并方式包括加权分数和 Reciprocal Rank Fusion。混合方法能同时保留关键词精确匹配和语义召回，但权重需要在评测集上调整，不能凭感觉设置。

### 4.7 Rerank 精排

召回阶段追求从大量文档中快速找到候选，Rerank 再使用更强的模型对少量候选重新评分。Cross Encoder 能同时阅读问题和文档，精度通常高于独立 Embedding，但计算成本也更高。

常见流程是先召回 20 至 100 个候选，再重排并选择前 3 至 10 个进入上下文。需要平衡效果、延迟和成本，并避免把内容近乎重复的多个块都交给模型。

### 4.8 Query Rewriting

Query Rewriting 根据对话和检索目标重写查询。例如把“那它支持多久”改写成包含产品名称和具体含义的独立问题。它还可以拆分多意图问题、补充缩写或生成多个查询。

重写的风险是改变用户意图或编造实体。系统应保留原始问题，并在评测中比较重写前后的召回效果。对明确的错误码或专有名词，原始查询往往比自由改写更可靠。

### 4.9 HyDE

HyDE 先让模型生成一段假设性答案或文档，再对这段文本做 Embedding，用它寻找真实文档。其直觉是问题与答案的表达形式不同，而假设文档更接近知识库文本。

HyDE 适合问题很短或语义抽象的场景，但会增加模型调用和延迟，生成内容也可能把检索方向带偏。它应作为可评测的查询扩展策略，而不是默认对所有请求开启。

### 4.10 Recall at K

Recall@K 衡量前 K 个召回结果是否覆盖了全部相关文档。若一个问题有四个相关块，前十个结果找到了三个，则 Recall@10 为 0.75。它适合评估召回阶段是否漏掉证据。

计算该指标需要人工或规则标注相关文档集合。标注不完整时，系统可能找到新的有效证据却被指标判错，因此应定期复核评测集。

### 4.11 MRR

Mean Reciprocal Rank 关注第一个相关结果出现的位置。若第一个相关结果排在第 2 位，该问题的倒数排名为 1/2；多个问题取平均得到 MRR。它适合用户通常只需要一个正确答案或首个证据的场景。

MRR 不关心第一个相关结果之后还有多少有效结果，因此不能单独用于需要多条证据的问题。

### 4.12 NDCG

Normalized Discounted Cumulative Gain 同时考虑结果位置和多级相关性。越相关的结果排得越靠前，得分越高；经过理想排序归一化后，分数通常位于 0 到 1 之间。

NDCG 适合比较重排效果，因为它能区分“高度相关”“部分相关”和“不相关”。代价是需要更细致的人工相关性标注。

### 4.13 RAG 如何串联

离线阶段先解析文档，保留结构和权限元数据，再按语义边界分块。每个块同时写入 BM25 索引和向量索引。在线阶段先根据对话改写查询，必要时使用 HyDE 扩展；随后执行混合召回，通过 Rerank 选择最有用且不重复的证据，最后把证据、来源和问题交给模型。

优化顺序通常是先建立可靠评测集，再检查解析与分块，然后比较 BM25、向量和混合召回，最后引入重排或查询改写。若没有 Recall@K、MRR 或 NDCG，开发者很难判断最终回答变差究竟是检索问题还是生成问题。

## 5 Agent 评测与稳定性

### 5.1 Trace

Trace 是一次 Agent 执行的完整轨迹，通常包含输入、模型请求、工具调用、节点状态、检索结果、耗时、Token 使用和错误。Trace 让开发者能够回答“系统为什么做出这个动作”，也是复现问题和构建评测集的基础。

Trace 应具有统一的任务 ID 和跨度关系，并对密钥、个人信息和敏感内容脱敏。只保存最终答案无法定位是路由错误、检索失败、工具参数错误还是模型判断错误。

### 5.2 Bad Case 分析

Bad Case 是没有达到预期的真实样本。分析时不应只改 Prompt，而应先对错误分类，例如意图识别、计划、检索、工具选择、参数、权限、恢复、答案或引用错误。

每个 Bad Case 应记录输入、期望行为、实际轨迹、根因、修复方式和回归测试。多个相似错误可以形成错误簇，帮助团队确定最值得优先修复的系统问题。

### 5.3 评测集

评测集是一组固定任务及其期望结果。数据来源可以包括产品需求、人工设计、历史 Trace 和 Bad Case。它应覆盖正常路径、边界条件、对抗输入和失败恢复，并按任务类型和难度分层。

防止评测失真需要版本化数据、固定判定规则并区分开发集与保留集。每次线上事故或重要 Bad Case 都应转化为回归样本。只有固定 Prompt、模型版本、工具环境和随机性设置，结果才具有可比性。

### 5.4 任务成功率

任务成功率是完成业务目标的任务数占总任务数的比例。关键是预先定义“成功”。例如创建工单任务需要检查工单是否存在、字段是否正确且没有重复，而不是只判断模型是否说“已完成”。

复杂任务可以同时设置总体成功率和阶段成功率。总体指标用于观察产品效果，阶段指标用于定位问题。

### 5.5 工具调用准确率

工具调用准确率可拆成工具选择准确率、参数准确率和调用时机准确率。模型选对工具但填错资源 ID，仍然不能算成功。对无需调用工具的问题，错误调用也应计入。

离线评测可以比较期望工具序列，线上还应结合实际业务结果。若允许多条合理路径，评测器需要接受等价方案，而不是要求完全相同的调用顺序。

### 5.6 证据有效率

证据有效率衡量答案中的关键结论是否被检索证据支持。它可以按引用精确性、引用覆盖率和证据与结论的一致性拆分。引用一个来源并不代表来源支持该结论。

评测时应把可验证陈述拆开，逐项判断证据是否充分。对没有证据的问题，可靠系统应表达不确定或拒绝回答，而不是补全听起来合理的内容。

### 5.7 延迟

延迟应观察分位数，而不只看平均值。P50 表示典型体验，P95 和 P99 暴露慢请求。Agent 的总延迟可以拆为路由、模型、检索、工具、数据库和排队时间。

优化时先找最大贡献项。并行调用独立工具、缓存稳定结果、减少不必要的 Agent 步数和使用分层模型都可能降低延迟，但不能以牺牲正确性和安全为代价。

### 5.8 超时与重试

每个外部调用都应有超时。重试适用于暂时性错误，如网络抖动、限流和部分服务错误，不适合权限拒绝、参数错误或确定性业务失败。指数退避和随机抖动能避免大量客户端同时重试。

重试预算应受总任务时限约束。若某一步已耗尽大部分时间，继续机械重试只会让用户等待更久。需要根据错误类型决定重试、降级、暂停或失败。

### 5.9 幂等

幂等表示同一个操作执行一次或多次，最终业务效果相同。网络超时会产生“不知道请求是否成功”的状态，因此外部副作用必须使用稳定幂等键或唯一约束。

例如创建工单前生成 `task_id + step_id` 作为幂等键，服务端保存键与结果。重试时若键已存在，直接返回原结果。仅在客户端记住“我调用过”不够，因为客户端可能在保存状态前崩溃。

### 5.10 断点恢复

断点恢复依赖持久化检查点、可重放输入和副作用账本。恢复流程先读取最后一个已提交状态，再核对正在执行的外部动作是否已经完成，最后从安全节点继续。

检查点粒度越细，重复计算越少，但写入成本越高。对于模型推理和检索等只读步骤，可以接受重新计算；对于付款、发送和发布等动作，必须确保不会重复产生业务影响。

### 5.11 权限隔离

权限隔离要求用户、Agent 和工具只获得完成任务所需的最小权限。认证回答“你是谁”，授权回答“你能做什么”。多租户系统还要在数据库查询和缓存键中携带租户边界。

高风险凭证不应进入模型上下文。更安全的做法是由受控工具代理在执行边界临时注入凭证，并记录谁在什么条件下调用了什么资源。不同 Agent 也应使用不同工具白名单。

### 5.12 Prompt Injection 防护

Prompt Injection 是不可信内容试图改变模型指令或诱导其泄露数据、越权调用工具。攻击内容可能来自用户输入、网页、文档、邮件或工具返回值。模型无法仅靠提示词可靠区分所有恶意指令。

防护需要分层完成：把外部内容标记为数据而非指令；限制可用工具和参数；在模型之外执行权限检查；对网络、文件和命令设置白名单或沙箱；敏感操作要求确认；输出和日志做脱敏；使用对抗评测持续回归。

### 5.13 评测与稳定性如何串联

系统先用 Trace 记录每次执行，再从失败轨迹中提取 Bad Case 并加入版本化评测集。离线评测计算任务成功率、工具准确率和证据有效率，性能测试记录 P50 与 P95 延迟。线上运行时，每个工具都有超时和分类重试，副作用使用幂等键，节点写入检查点。权限代理与注入防护限制模型造成的影响范围。这样形成“观察、归因、修复、回归、上线监控”的闭环。

## 6 LLM 基础与优化

### 6.1 Transformer

Transformer 是现代大语言模型的核心架构。文本先被 Tokenizer 转换为 Token ID，再映射成向量。自注意力机制让每个位置根据其他位置的信息更新表示，多层网络逐步形成上下文表示，最终预测下一个 Token 的概率分布。

注意力通过 Query、Key 和 Value 计算相关性。多头注意力允许模型同时关注不同关系，位置编码提供顺序信息。训练的基本目标通常是根据前文预测后文，因此模型本质上生成高概率续写，并不天然连接真实世界或保证事实正确。

这解释了三个工程结论：最新或私有知识需要外部检索；真实操作需要工具；正确性和权限必须由系统验证，而不能仅相信自然语言输出。

### 6.2 Prompt Engineering

Prompt Engineering 是通过指令、上下文、示例和输出约束，引导模型完成任务。清晰 Prompt 通常包含角色或任务、输入、约束、允许的工具、输出格式和失败处理。

优化 Prompt 应基于评测集，而不是只看几个演示样例。指令应具体说明可观察行为，例如“没有证据时返回证据不足”，比“请准确回答”更可测试。Prompt 不能代替鉴权、数据校验和业务规则。

### 6.3 Few shot

Few-shot 在 Prompt 中提供少量输入输出示例，让模型模仿任务边界和格式。它适合分类标准、结构化抽取和特定表达风格。示例应覆盖容易混淆的边界，并保持格式一致。

示例会占用上下文，也可能导致模型机械模仿。应比较零样本与少样本效果，并防止示例包含敏感数据。若规则频繁变化，维护明确规则可能比堆积示例更可靠。

### 6.4 Function Calling

Function Calling 是模型根据工具 Schema 生成函数名称和结构化参数的能力。它是 Tool Calling 的模型侧机制；应用侧仍需完成验证和执行。模型不会真正运行函数，也不能因为参数符合 Schema 就被视为获得权限。

设计 Schema 时应减少歧义、使用枚举、给字段清晰描述，并把高风险动作拆成准备和确认两步。工具返回值也应结构化，方便模型和程序判断成功、失败或需要重试。

### 6.5 SFT

监督微调使用输入和理想输出样本继续训练预训练模型，使其更稳定地遵循特定任务或风格。它适合有较多高质量标注数据、基础模型行为与目标存在稳定差距的场景。

SFT 会改变模型参数，需要数据清洗、训练资源、验证集和部署维护。它不适合注入频繁变化的事实知识，这类问题通常应使用 RAG。微调前应先确认 Prompt、工具和检索无法以更低成本解决问题。

### 6.6 LoRA 与 QLoRA

LoRA 冻结基础模型权重，只训练插入注意力或其他线性层的低秩矩阵，因此需要更新的参数更少。它降低训练和存储成本，并可为不同任务保存不同适配器。

QLoRA 在此基础上把基础模型量化为较低精度，以进一步降低显存占用，同时训练 LoRA 参数。它使单机微调大模型更可行，但仍需关注量化误差、训练稳定性和推理部署支持。

LoRA 和 QLoRA 是训练效率方法，不自动保证数据质量和任务效果。是否采用应通过基线评测、训练成本和上线收益共同决定。

### 6.7 LLM as a Judge

LLM-as-a-Judge 使用一个模型按评分标准评价另一个模型的输出。它适合评估开放式回答的相关性、完整性、忠实度和表达质量，成本通常低于全量人工评审。

Judge 可能受位置、长度、措辞和模型偏好影响，也可能无法识别自己不了解的事实。可靠做法包括提供明确评分 Rubric、随机交换候选顺序、要求引用证据、使用人工样本校准，并报告 Judge 与人工的一致性。涉及安全和关键业务结果时，不能只依赖单一 Judge。

### 6.8 LLM 基础与优化如何串联

Transformer 的生成机制决定了模型擅长语言模式但不保证事实和行动安全。Prompt 与 Few-shot 是最低成本的行为引导；Function Calling 把自然语言意图转成结构化工具请求；RAG 为模型提供可更新知识；当任务行为仍有稳定差距且拥有高质量数据时，再考虑 SFT 或 LoRA。QLoRA 用于降低训练资源，LLM-as-a-Judge 则可以辅助规模化评测，但需要人工校准。

## 7 五类能力的完整系统链路

### 7.1 企业知识与任务助手案例

假设用户提出：“查找公司的差旅制度，判断这张报销单是否合规；若不合规，生成修改建议，不要直接提交。”

1. FastAPI 接收请求，验证用户身份、租户、报销单结构和权限，并在 PostgreSQL 中创建任务。
2. 路由器选择财务规则 Agent。LangGraph 读取任务状态，外层计划分为检索制度、抽取报销信息、规则比对和生成建议。
3. RAG 管线将用户问题改写为独立查询，通过 BM25 与向量混合召回制度条款，再用 Rerank 选择最相关证据。
4. Agent 通过结构化输出提取金额、城市、日期和票据类型。程序对字段和枚举做二次校验。
5. 确定性规则负责金额上限等明确判断，模型只解释规则与证据。由于用户要求不提交，工具白名单不包含提交接口。
6. 每个节点记录 Trace、耗时、模型版本、检索证据和工具结果。任务状态和检查点写入数据库，短期进度可写入 Redis。
7. 如果模型或检索服务超时，系统按照错误类型有限重试。若进程重启，则从检查点恢复。该场景没有外部提交副作用，但仍保留任务幂等键。
8. Pytest 覆盖正常单据、超标单据、缺失字段、无权限访问和注入攻击。离线评测统计任务成功率、证据有效率、Recall@K 和 P95 延迟。

这条链路展示了完整职责分配：模型理解和生成，检索提供证据，确定性代码执行规则，工具接触外部系统，状态层保证恢复，策略层控制权限，评测层验证效果。

### 7.2 数据流与控制流

数据流回答“信息在哪里移动”：用户输入进入 API，文档进入索引，证据进入模型，结果写入数据库。控制流回答“下一步由谁决定”：状态机判断节点，模型提出工具调用，策略层批准或拒绝，Worker 执行。把两者分开设计，能避免把业务状态埋在聊天记录中，也能让权限检查独立于模型判断。

### 7.3 可靠系统的三条边界

- 模型边界：模型输出始终视为待验证建议，结构化输出也需要业务校验。
- 副作用边界：真正改变外部系统的动作必须经过权限、审批、幂等和审计。
- 证据边界：回答中的事实应能追溯到文档、数据库或工具结果；证据不足时明确说明。

### 9.3 高频追问

**为什么使用异步接口不一定更快**

异步主要提高 I/O 等待期间的并发利用率。若数据库驱动仍是同步的，或者在事件循环中执行 CPU 密集任务，异步接口可能没有收益，甚至阻塞其他请求。

**ReAct 与 Plan and Execute 怎样选择**

探索性强、下一步依赖即时观察的任务适合有限步数的 ReAct；步骤和依赖较明确、需要审计或恢复的任务适合 Plan and Execute。复杂系统可以外层计划、内层 ReAct。

**为什么混合检索通常优于只用向量检索**

向量检索擅长语义相似，BM25 擅长错误码、编号和专有名词。混合召回能覆盖两类信号，但是否更好必须通过同一评测集验证。

**结构化输出为什么仍会失败**

Schema 只能保证格式和基础类型，不能保证实体存在、业务关系正确或用户有权限。程序仍需执行语义和权限校验。

**重试怎样避免重复操作**

为副作用生成稳定幂等键，服务端用唯一约束保存调用结果。客户端超时后先用相同键查询或重试，服务端返回原结果，而不是再次创建资源。

**什么时候应该微调而不是继续优化 Prompt 或 RAG**

当任务行为存在稳定差距，已有足量高质量训练数据，而且 Prompt、工具和检索已无法以更低成本解决时，才考虑 SFT 或 LoRA。频繁变化的事实知识优先使用 RAG。

## 10 专业技能总结

AI Agent 工程师的核心能力，是把概率性的模型放进一个可验证、可恢复、受权限约束的软件系统。Python 和后端技术提供可靠服务；Agent 编排把目标变成步骤；RAG 把外部知识变成可引用证据；评测体系证明系统是否完成任务；超时、幂等、检查点和权限控制限制失败影响；Transformer 和微调知识则帮助开发者判断模型能力与优化成本。

可以用一条主线记住全部知识：请求通过 API 进入系统，身份和输入先被校验；Agent 根据状态规划动作；检索系统提供证据；工具代理执行经过授权的操作；数据库保存事实与检查点；Trace 记录全过程；评测集把 Bad Case 变成回归测试；必要时再通过 Prompt、Few-shot、RAG 或微调改善模型行为。

真正达到“掌握”的标志不是能背诵术语，而是能回答以下问题：为什么选择这项技术，失败会发生在哪里，如何观察和恢复，怎样防止越权或重复副作用，以及用什么测试和指标证明改动有效。把每项简历技能都落实到一个可运行示例、一组测试和一份真实评测报告，专业技能才会从零散接触变成可解释、可复现的工程能力。
