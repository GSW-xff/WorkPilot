## 一、先定调：这个项目在简历上「卖」的是什么

面试官看一个 Agent 项目，最怕看到的是「调了个 LLM + 几个工具 + LangChain 拼起来的 Demo」。
WorkPilot 的差异化在两点，简历必须围绕这两点写：

| 卖点 | 一句话 | 对应证据 |
| --- | --- | --- |
| **不是让模型自由发挥，而是让模型产出受约束的结构** | 模型只负责产出候选计划，合法性、风险、审批、副作用全部由确定性代码裁决 | `dag.py` / `policy.py` / `runtime.py` |
| **不是「跑通一次」，而是「可中断、可恢复、可审计」** | 审批可挂起数天、进程崩溃可从检查点恢复、每一步都有远端验证和审计产物 | `workflows/temporal.py` / Action Ledger / Checkpoint |

一句话定位（建议放在项目名下面作为副标题）：

> 把自然语言目标转成可审计、可中断、可恢复的结构化任务 DAG，在人工审批与幂等约束下安全执行外部写入。

## 二、推荐版本（标准版，约 400 字，4–5 条）

> **WorkPilot — 面向企业办公流程的安全执行 Agent 运行时** ｜ 独立开发（个人项目）｜ 2026.03 – 2026.10
> 技术栈：Python 3.12、FastAPI、Pydantic v2、Temporal、PostgreSQL、SQLAlchemy 2、OpenTelemetry、Playwright、MCP

- **架构搭建**：按「接入—规划—编排执行—持久化」四层解耦。用 Pydantic v2 定义 TaskPlan、ActionLedger 等领域模型；以 `Protocol` 抽象 ModelGateway 与 ToolAdapter，能力注册表统一管理 API / MCP / Browser 三通道工具及其固有风险等级；FastAPI 提供任务、审批、回放接口与 SSE 事件流；SQLAlchemy 2 + Alembic 持久化，PostgreSQL RLS 做租户隔离。
- **任务编排**：自然语言目标先经 fail-closed 支持域门判为「可执行 / 需澄清 / 拒绝」，再由模型输出符合 JSON Schema 的 TaskPlan，校验失败仅允许一次修复、仍不合法则安全回退确定性模板；计划通过无环性、能力、风险等级、步骤上限校验后按拓扑序调度，每步执行前由 R0–R3 策略引擎决定放行或审批，R2 级外部写入须经参数哈希绑定的人工审批。
- **副作用控制**：执行前以幂等键在 Action Ledger 预占动作；结果未知时先查远端状态再重试（lookup-before-retry）；执行后用独立 verify 调用核验远端真实状态，避免「以为成功」；每步写入检查点与时间线，形成可重放的审计链。
- **长任务编排**：用 Temporal Workflow 承载跨小时、跨天的任务，Activity 驱动状态推进，Update 接收人工审批，Signal 处理暂停 / 恢复 / 取消，审批等待 7 天超时自动取消，进程崩溃后可 replay 恢复；事件经 Outbox 与业务事务同写，保证至少一次投递。
- **工程闭环**：构建 60 条版本化任务集的离线确定性回归与 CI 零容忍安全门禁，180 次回归中未授权写入由 0.3333 降至 0；接入 OpenTelemetry Trace、Prometheus 指标与故障注入测试建立可复现证据。

## 四、详细版（约 550 字，项目经历作为简历核心时用）

在标准版基础上，把「架构搭建」和「编排」各拆成两条，并补充上下文工程：

- **分层架构**：接入层 FastAPI + SSE 实时事件流；规划层 ContextBuilder 做上下文组装；编排层 DAG 调度 + 策略引擎 + 状态机；执行层能力注册表 + 多通道适配器；持久层 SQLAlchemy 2 + Alembic + PostgreSQL RLS。各层以 Protocol / 抽象仓储解耦，可替换为内存实现做单测。
- **上下文工程**：ContextBuilder 按 system_invariants → user_goal → organization_policy → tools → 检索结果分层组装，每条上下文带 trust label（system / trusted / untrusted）；不可信内容自动包裹 `<external_data>` 并检测 Prompt Injection 标记，按优先级与 Token 预算裁剪，超预算来源显式记录为 omitted。
- **计划生成**：fail-closed 支持域门先于任何模型调用执行；模型结构化输出后做一次 repair，仍不合法则回退确定性 DemoPlanner，保证规划永不静默失败。
- **执行编排**：拓扑序调度 → 策略裁决 → 参数哈希审批 → 幂等预占 → lookup → execute → verify → 检查点，任一环节失败即进入终态或待恢复态，不允许跳过验证。
- **重规划安全**：Plan Diff 明确列出新增 / 删除 / 修改步骤，禁止删除或篡改已成功步骤，避免重复副作用。
- **可观测与评测**：OTel Trace 覆盖 policy.evaluate / tool.execute / tool.verify 各段，Prometheus 记录策略拒绝、工具错误、重复调用等指标；评测产出机器可读报告与人工盲审包。

## 五、面试口述稿：被问「这个 Agent 是怎么编排的？」

控制在 60 秒内，按「一条主线 + 三个约束点」讲：

> 我把一次任务拆成规划和执行两段，中间用一份结构化计划做契约。
>
> 规划段：用户给一句自然语言，我先不过模型，而是走一个 fail-closed 的支持域门——不在支持范围内就返回「需澄清」或「拒绝」，这三类是一等状态，不是异常。过了门之后才调用模型，强制它输出符合 JSON Schema 的 TaskPlan，也就是带依赖关系的 DAG。拿到之后我不信它，用确定性代码校验：有没有环、工具存不存在、风险等级够不够、步骤数超没超上限。校验失败只允许修一次，还不行就回退到一个确定性的模板计划。
>
> 执行段：按拓扑序遍历每一步，每一步都要过策略引擎，风险分 R0 到 R3，R2 以上必须人工审批，而且审批绑定的是参数的哈希——参数一改，审批自动失效。真正执行前先用幂等键在账本里占个位，防止重复触发；如果执行结果未知，先去远端查状态再决定重不重试，不盲目重试；执行完还要单独调一次远端验证，确认副作用真的发生了。
>
> 整个过程每一步都写检查点和时间线，长任务交给 Temporal——审批可以挂几天，服务重启了能 replay 回来。

**三个追问高发点，务必准备：**

1. **「为什么不让模型直接决定下一步？」** → 因为模型的决策不可复现、不可审计，也没法做回归测试。我把「生成候选」和「裁决合法性」分开，模型只做前者，后者全用确定性代码，这样才能建立 60 条任务集的回归门禁。
2. **「参数哈希审批解决了什么问题？」** → 解决审批后参数被篡改（TOCTOU）。预览时算一次哈希，执行前再算一次，不一致就让审批失效重新批。
3. **「lookup-before-retry 是什么场景？」** → 连接器超时/响应丢失时结果未知，直接重试可能造成重复写入。账本把状态标为 UNKNOWN 并要求对账，重试前先查远端是否已存在该对象。故障注入里同动作投递 100 次，远端对象仍只有 1 个。

## 六、可写与不可写清单（重要）

### 可以写

- 60 条版本化任务集 × 3 次 = 180 次**离线确定性**回归，未授权写入由 0.3333 降至 0
- 20 条 Agentic 安全回归全部通过
- 真实 Temporal 本地测试服务故障注入通过（Worker 重启、Update 继续、幂等投递、History replay）
- PostgreSQL RLS 对抗测试通过（本地容器）
- 300 ops / 并发 20 / 0% 错误 / 813.90 req/s（内存仓储、in-process ASGI）
- 搭建了双模型评测与 GitHub 沙箱验收工具链（只写「搭建工具链」）

### 不能写

- 真实云模型的质量、成本、成功率 —— 没有外部凭证，没有实测报告
- GitHub OAuth 沙箱端到端已通过 —— 同上
- 生产 SLO、99.9% 可用性、多区域恢复 —— 只有 SLO 计算口径文档，没有生产运行数据
- 5 人可用性研究、SUS 分数 —— 只有可执行协议，没有参与者
- 多 Agent 优于单 Agent —— 见 ADR-003，仓库明确不作此结论

### 数字必须带的限定词

> 凡出现「180 次回归 / 未授权写入 0 / 813.90 req/s」等数字，同句或紧邻句必须出现
> **「离线确定性 Planner」**或**「内存仓储、非生产容量」**。单独写成功率会被追问到穿帮。

- 简历上可附仓库链接；若仓库尚未公开，至少准备一份可运行的本地 Demo（`make check` + `uv run workpilot`）。
