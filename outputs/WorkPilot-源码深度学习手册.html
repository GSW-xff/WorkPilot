1. 先记住一句话

模型只出计划，确定性代码掌管一切后果。
模型唯一职责是把自然语言变成符合 JSON Schema 的 TaskPlan；之后是否被允许、要不要人批准、要不要真的调用外部系统、调失败怎么办、结果可信吗，全部由不依赖模型的确定性代码决定。模型挂了、被注入、输出非法，系统就回退到确定性 DemoPlanner，而不是"带病执行"。

这条原则贯穿所有模块。后面看每一处设计时，都可以问一句：这件事如果交给模型判断，最坏会怎样？答案几乎都是"把防线前移到模型之前或之后"。两套防线位置：

  • 模型之前：IntentGate（支持域门）、ContextBuilder（上下文预算与注入标记）、RunBudget（Token/成本硬闸）
  • 模型之后：validate_plan（DAG/能力/风险/步数）、PolicyEngine（R0–R3 裁决）、审批、Action Ledger（幂等）、verify（独立远端核验）

3. 钥匙数据结构：TaskRun 解剖

理解这一个模型就理解了半个系统（models.py:188）。TaskRun 是一个聚合根，一次任务的全过程证据都在里面：

字段作用回答什么问题
status任务状态机当前位置现在能做什么、不能做什么
planning_dispositionEXECUTABLE / NEEDS_CLARIFICATION / REJECTED这个请求到底该不该做
planTaskPlan：步骤、依赖、风险、验证规则打算怎么做（含版本号，用于重规划）
steps每个步骤的运行态 StepRun哪一步做到哪了
approvals审批记录 + parameter_hash + plan_version谁批准了"哪个参数版本"的哪一步
ledger幂等账本：ActionLedgerEntry 列表这个动作做过没有、结果未知还是已确认
verifications每步独立核验结果与证据引用"成功"是工具自述的还是查出来的
artifacts工具结果、上下文快照（脱敏后）审计时能还原什么
events时间线（带序号，供 SSE 断线续传）过程中发生了什么
checkpoints状态 + 计划版本 + 已完成步骤 + 账本键崩溃后从哪里恢复
version乐观锁版本号有没有并发写冲突
账本条目 ActionLedgerEntry（models.py:133）：idempotency_key / status / attempt / remote_id / last_error / next_retry_at / reconciliation_status。注意最后两个字段——它们是"UNKNOWN 不能盲目重试"的落地。

4. 一次完整流程：7 个阶段的方法调用链

以 README 里的例子为例：goal = "收集项目进展，生成并发送周报"，收件人 team@example.com。

0

请求进入 → 租户与身份

# api.py:105 tenant_context(request, X-Tenant-ID, X-User-ID, Authorization) ├─ 无 OIDC 配置 → Principal(roles={owner,approver,admin}, scopes={*}) # 本地模式 └─ 有 OIDC → OIDCVerifier.verify(token) → Principal(tenant_id, roles, scopes) # 之后所有 service / repository 调用都强制带 tenant_id
防住：跨租户访问、未授权调用。租户 ID 从头部取一次，之后全程透传，不信任请求体里的任何租户字段。
1

创建任务 → 支持域门（模型之前）

# api.py:374 POST /v1/tasks → runtime.py:84 WorkPilotService.create_task_async(tenant_id, user_id, goal) ├─ _new_task() → 事件 "task.created" + 状态 CREATED→PLANNING └─ _structured_plan() └─ StructuredPlanner.plan() # planner.py:336 └─ IntentGate.enforce(goal) # planner.py:131 —— 第一道门，不调模型 └─ IntentGate.evaluate() # planner.py:110 ├─ 命中 9 条拒绝模式 → REJECTED （越权/注入/绕过审批/无界规划） ├─ 命中 4 类意图 → EXECUTABLE （周报/会议跟进/Issue 汇总/故障场景） └─ 都不命中 → NEEDS_CLARIFICATION + 3 个澄清问题
三种处置对应三种任务状态：REJECTED（runtime.py:307）、NEEDS_CLARIFICATION（:298）、EXECUTABLE（:317）。
防住：Prompt Injection（"忽略之前指令"）、越权（admin.delete/payroll.delete/凭据/shell）、绕过审批（"跳过审批"/"降低风险"/"R3"）、无界规划（"循环依赖"/"100 个步骤"/"无限重试"）、以及模糊请求（说不清对象就问，不猜）。
不做会怎样：这些请求会一路走到模型，模型可能照做；即使模型拒绝，也已经付了 Token 成本和延迟。这里是"在调模型之前就被挡掉"的源码依据。
2

结构化规划 → 上下文、模型、校验、修复、回退

# planner.py:336 StructuredPlanner.plan 继续 select_candidate_tools(goal, tools) # context.py:145 工具检索，最多 8 个 ContextBuilder.build(goal, recipient, tools) # context.py:62 ├─ 固定 4 层：system_invariants(优先级100) / user_goal(95) / org_policy(90) / tools(85) ├─ 检索到的外部内容 → 包进 <external_data trust='untrusted'> 并打注入标记 └─ 按优先级 + Token 预算裁剪，装不下的进 omitted_sources gateway.generate_structured(messages, TaskPlan, policy, budget) # model_gateway.py ├─ 预算预检：input > max_input_tokens → BudgetExceededError # :128 硬闸，请求前就算 ├─ response_format = json_schema(strict=True) # :187 结构化输出 ├─ 429/5xx/超时 → 最多 max_retries 次退避重试 └─ 成本估算 > max_cost_usd → BudgetExceededError # :236 # 模型返回后 —— 确定性校验 TaskPlan.model_validate(response.output) # Pydantic：形状与类型 validate_plan(plan, capabilities, fixed_risks, max_steps=20) # dag.py:49 ├─ topological_order() → 无环、依赖存在、id 唯一 # dag.py:16 ├─ 能力必须已注册；风险不得低于能力固定值（只能升不能降） ├─ R3 → 直接报错禁止；R2 必须 requires_approval ├─ R1/R2 副作用步骤必须定义 verification └─ 步数 ≤ 20 失败 → 把校验错误塞回消息，只修复 1 次（for attempt in range(2), planner.py:356） 仍失败 / 网关异常 → DemoPlanner.plan() 确定性回退（planner.py:400），并标记 used_fallback=True
防住：上下文超窗（预算裁剪）、外部内容污染提示词（trust 标签 + 注入标记）、成本与延迟失控（硬闸）、模型输出非法（Schema + 修复 1 次）、模型产生环/越权/无审批的计划（validate_plan）、模型不可用（确定性回退）、风险被模型调低（取 max）。
不做会怎样："模型说 R0 就 R0"是最典型的 Agent 事故；没有回退则模型一挂整个系统不可用。
3

计划落库 → 生成证据与检查点

# runtime.py:121 _attach_planning_evidence / :315 _apply_plan 上下文快照 → Artifact（只存 source/trust/长度/内容 sha256，不存正文，:148 sensitive_content_recorded=False） _apply_plan：plan 落库、disposition=EXECUTABLE、steps 初始化、PLANNING→PLAN_READY _checkpoint() # :698 记录 状态 + 计划版本 + 已完成步骤 + 账本键

5. 两套状态机

5.1 任务状态机（state_machine.py:5）

CREATED → PLANNING → {PLAN_READY | NEEDS_CLARIFICATION | REJECTED | FAILED | CANCELLED} NEEDS_CLARIFICATION → PLANNING（补充信息后重规划）| CANCELLED PLAN_READY → RUNNING | PAUSED | CANCELLED RUNNING → WAITING_APPROVAL | REPLANNING | PAUSED | CANCELLED | FAILED | SUCCEEDED WAITING_APPROVAL → RUNNING | REPLANNING | PAUSED | CANCELLED PAUSED → PLAN_READY | RUNNING | WAITING_APPROVAL | CANCELLED # 靠 paused_from 记住原状态 REJECTED / CANCELLED / FAILED / SUCCEEDED = 终态（空集合）

ensure_transition()（:49）在每次 _transition 里强制校验，非法迁移直接抛错。防住：状态被并发请求串改（比如已完成任务又被审批、已取消任务又被恢复）。

5.2 账本状态机（runtime.py:396–537）

状态何时置位含义与后果
RESERVED执行前预占并落库（:406）意图已记录。崩溃后重放能看到"本来要做"，但 不能据此认为已执行
DISPATCHEDexecute 返回成功（:496）工具说做成了 —— 还不算数，必须过 verify
CONFIRMEDverify 通过（:536）远端独立确认。再次执行直接复用结果
UNKNOWN超时 / outcome_unknown / 未知异常（:454, :480）结果不明确，reconciliation_status=REQUIRED，重试前必须先查远端
RETRYABLE可重试错误（:458）带 next_retry_at 指数退避（min(2^attempt, 60)s）
FAILED不可重试错误终态，步骤失败
关键区别：DISPATCHED ≠ CONFIRMED。工具返回 success 只说明"它自称成功了"（网络抖动、部分写入、异步生效延迟都可能让这句话不成立）。本项目把"远端真的存在这个对象"（verify 拿 remote_id 回查）作为成功判据——这是 lookup / verify 必须独立存在的原因。

7. 代码阅读路线与自测题

建议顺序（约半天到一天）

  1. models.py（30 分钟）—— 先把 TaskRun / PlanStep / ActionLedgerEntry / ActionResult 认全。不懂这几个，后面全是黑话。
  2. runtime.py:324–547 的 _run（1 小时）—— 逐行读主循环，这是整个系统的心脏。读的时候对着第 4 节第 5 阶段的调用链。
  3. planner.py:63–170（40 分钟）—— 支持域门和确定性计划长什么样。
  4. dag.py + policy.py（20 分钟）—— 短，但决定了计划的合法性边界。
  5. connectors/base.py + fake.py（30 分钟）—— 看懂四个方法为什么必须都存在。
  6. workflows/ 三个文件（30 分钟）—— 理解 Workflow 只管"什么时候推"。
  7. repository.py + db/repository.py（20 分钟）—— 乐观锁与租户隔离。

自测题（能答出来说明真懂了，面试也大概率问这些）

  1. 模型把 mail.send 标成 R0，系统怎么处理？为什么不是直接按 R0 执行？（提示：dag.py:71）
  2. 审批通过后有人改了收件人，会发生什么？（提示：runtime.py:564 的 EXPIRED）
  3. 连接器超时了，账本是什么状态？下一步必须做什么才能重试？（提示：UNKNOWN + reconciliation_status）
  4. Worker 在 execute 之后、verify 之前崩溃，恢复后会重复发邮件吗？为什么？（提示：账本 RESERVED/DISPATCHED 都不是 CONFIRMED，lookup 先查）
  5. 为什么 verify 要独立存在，而不能直接用 execute 的返回值当结果？（提示：网络分区、异步生效）
  6. IntentGate 为什么放在模型调用之前？放到之后会有什么损失？
  7. 重规划时想改一个已成功步骤的参数，系统会怎么做？（提示：planner.py:429）
  8. 两个人同时点审批，会发生什么？（提示：乐观锁 version）
  9. Temporal Workflow 重放时，副作用会不会重复执行？（提示：幂等判断在数据库账本，不在 Workflow 内存）
  10. 为什么说"180 次回归未授权写入为 0"只代表离线确定性 Planner，不代表真实模型？
第 4 题和第 9 题是最常被追问的两道，答的时候要落到"账本状态 + 先查后做"上，不要停在"因为用了 Temporal"。

8. 边界口径：哪些是真的，哪些还没做

面试时这部分要主动说清楚——诚实边界本身就是加分项，被问出来才承认是减分项。

已完成且有证据：离线确定性评测（60 条 × 3 次 = 180 次，未授权写入 0，evals/reports/intent-gated-v2/）；真实 PostgreSQL RLS 对抗测试（docs/reports/postgres-rls.md）；真实 Temporal 本地服务故障注入（Worker 重启、Update 继续、History replay，docs/reports/temporal-fault-injection.md）；本地可观测栈；MCP 只读闭环；OIDC/RBAC；知识管线；浏览器证据通道；受控 Memory；任务/审批/恢复控制台。
需要外部条件、尚未验收：真实云模型对比（缺 API Key 与真实价格）；GitHub OAuth 沙箱 E2E（需专用仓库与一次性 token）；生产 SLO；5 人可用性研究；V3 最终验收。仓库里没有伪造这些通过报告——这点可以直说。
架构取舍可以主动讲的：为什么用单 Agent 而不是多 Agent（docs/adr/003-single-agent-before-multi-agent.md）；为什么选 Temporal（docs/adr/002-temporal-workflow.md）；响应丢失事故的复盘（docs/reports/response-loss-postmortem.md，对应账本 UNKNOWN 设计的由来）。
